同频提问局｜产品说明计划书

一、项目概述与核心创作思路

同频提问局以共同问题连接人，让参与者通过一次经验交换形成自己的理解，再决定是否继续交流。 项目面向“灵魂匹配局：社区连接与兴趣社交”赛道，选择知识交换与小型共创作为产品方向。

用户可能读过很多回答，却仍不知道如何把建议用到自己的情境；也可能有值得分享的经验，却找不到合适的交流对象。项目希望将“对同一问题感兴趣”转化为一次具体互动，降低开场压力，让交流留下可继续使用的成果。

核心路径为：共同问题 → 双向贡献 → 复述补充 → 新理解卡 → 自愿继续。 网页中的“问题卡片”承载新理解卡的成果形式。这条路径是产品设计目标，当前主项目已建立问题、交流、成果与关系模块，贡献引导和完整结束流程仍需完善。

以问题作为连接单位

一个明确的问题同时提供主题、参与理由和交流边界。参与者可以根据自己是否关心问题、是否有可分享的经历，主动选择加入。当前采用人工选择同一问题的方式，不依赖算法评分。

让不同经验产生互补

双方既可以提出需求，也可以贡献方法、案例、观察或整理能力。设计中的“一给一求”强调互惠，不要求每个人都是专家。主项目现有表单记录昵称和学习诉求；独立的贡献字段、任务提示与复述引导属于待完善设计。

把交流整理为共同成果

产品鼓励双方用自己的话说明收获，保留有用的关键句与尚待验证的内容。成果卡帮助参与者回顾讨论，并成为下一次实践或讨论的起点。双方确认表达的是完成整理的意愿，不代表系统已验证答案正确。

让关系自然延续

一对一讨论可以扩展为本产品内的疑问社区话题。用户也可以主动申请好友，经过对方同意后再建立联系。好友、成就和动态形象围绕互助过程提供反馈，核心价值仍是共同问题带来的真实交流。

二、目标用户、痛点与产品价值

优先面向有具体学习、求职或兴趣实践问题的学生和初入职场者，以及愿意分享经验的参与者。先服务一次范围明确的交流，再验证用户是否愿意持续参与。

用户与场景主要痛点产品回应预期价值
学生与跨专业学习者看过方法，但不知道如何应用，也不容易找到交流伙伴围绕具体学习问题邀请他人补充经验从理解知识走到一次小实践
初入职场者问题过于宽泛，获得的建议难以执行明确情境和希望得到的帮助，围绕一个目标交流获得更贴合实际条件的下一步
兴趣学习者想认识同好，却不知如何开场先选择共同问题，再交换做法与观察降低陌生交流的压力
愿意帮助他人的参与者单向回答投入大，难以看到自己的帮助产生什么结果双方整理收获，以成果卡和成就记录互助看见贡献价值，形成再次参与的理由

以上是产品假设，不是已取得的用户增长或效果数据。需要通过自愿参与者试用，验证问题是否容易理解、交流是否双向、成果是否值得保留。

三、产品流程与功能说明

1. 从问题板块进入

网页包含学习、求职、职场适应、技能提升、生活规划和兴趣社交六类问题入口。用户可以发布自己的问题，或选择愿意参与的问题。示例问题用于解释操作，不代表真实参与者或知乎检索结果。

2. 发布并选择共同问题

当前主项目的提问表单包含板块、问题、昵称和选填的学习诉求。回应者选择问题后填写昵称和自己希望解决的内容，进入同一房间。匹配以用户主动选择为依据。

后续将围绕“当前卡点、期望收获、可贡献内容”完善表达提示，并增加发布预览，帮助双方提前判断是否适合交流。

3. 围绕问题持续交流

交流房间显示原问题和参与角色，支持发送文字消息。双方可以澄清情境、举例和补充经验。设计上鼓励“先回应、再复述、最后提出新理解”，这一方法尚未形成必须逐步完成的工作台。

4. 按需扩展为疑问社区

参与者可以把房间扩展为话题，其他人主动加入后参与讨论。话题保留原问题、消息和成员关联。这里的“疑问社区”是本产品内部模块，并不代表已向知乎站内发布内容。

计划在扩展前增加范围预览和双方同意步骤，让参与者清楚哪些内容会被更多人看见；目前不能把一对一界面等同于受权限保护的私密空间。

5. 整理成果

当前原型提供关键句选择、双方总结和结束确认，通过双方确认状态触发问题卡生成。卡片包含原问题、双方总结及选中的关键句，可分类、复制、调用系统分享或删除；设备不支持系统分享时使用复制。

当前总结和关键句允许留空，进入整理后普通一对一发言会暂停。因此“形成有效收获”和“取消整理后恢复交流”仍是待完善项，不能仅以出现一张卡片认定问题已解决。

6. 自愿继续与互助反馈

好友申请从共同房间发起，对方通过后形成关系，可按提问者、解决者、社群好友或自定义分区管理。“学到了”和“解决了”成就按完成房间记录互助，避免同一房间重复累计。成就不作为专业能力或身份信用证明。

四、典型使用场景

校园学习：把阅读收获变成一次实践

以下为产品设计示例，不是已发生的用户案例。

一位学生读到关于阅读方法的讨论，提出“怎样把一篇读书笔记讲成别人听得懂的分享？”另一位有社团分享经验的参与者选择加入，希望同时学习如何整理提纲。

双方从具体卡点出发：提问者提供一段自己的表达，回应者分享“结论—例子—问题”的组织方法；随后互相复述，判断哪里仍不清楚。预期成果是一张记录双方收获与“试讲一段、记录反馈”行动建议的问题卡。若还有跨学科表达问题，可以主动邀请社区成员补充。

该场景的价值在于把已有知识放进个人情境，通过互相解释发现理解差异，并留下一个能继续实践的结果。

初职场：把宽泛请教变成情境讨论

围绕“怎样向同事提出一个清楚的协作请求”，参与者交换具体表达和经历，比较不同约束下的做法。卡片保留适用条件与各自收获，帮助用户再次遇到类似场景时回看，而非承诺给出普遍正确的职场答案。

兴趣实践：用共同任务开始认识同好

摄影或写作初学者可以围绕一个具体作品思路交流观察，选出一个小练习作为下一步。参与者通过贡献了解彼此，是否成为好友由双方决定。

五、与知乎社区生态的契合度

以问题组织交流，承接真实求知动机

知乎的问题、回答与评论承载不同经验和观点。项目沿用这种围绕问题展开表达的方式，把“我关注这个问题”作为参与理由，使知识兴趣成为人与人之间的连接入口。

这种契合首先体现在产品组织方式上，不以已有平台接入作为前提。当前主项目仍使用自创示例与用户输入，尚未形成真实知乎内容驱动的交流流程。

在已有讨论基础上，补充个人情境中的共同理解

知乎社区已经包含经验分享、追问和讨论。同频提问局拟补充的是小范围、双方参与的实践整理：读者带着自己的约束重新描述问题，与另一位自愿参与者交换做法，把“看过”推进到“能说清楚下一步”。

对用户而言，价值是降低参与门槛并获得更具体的反馈；对社区而言，预期价值是增加有背景、有实践依据的讨论素材。是否产生更高质量的持续贡献，需要真实试用后验证。

保留知识来源，让成果可以回到原讨论

拟采用的内容路径是：公开问题或必要摘要 → 原文链接 → 用户自己的情境问题 → 自愿交流 → 人工确认的成果卡。

后续来源记录应包含来源链接、内容标识、引用摘要、可使用范围和人工核验状态。涉及引用时优先使用必要摘要并引导阅读原文，明确区分原作者观点与参与者新形成的理解。

成果回到知乎，应由用户检查引用和共同内容的分享意愿，再自行决定是否整理为回答或评论。当前没有自动回写知乎的能力，也不会自动替用户发布。

社交连接建立在自愿参与上

被引用作者是资料来源，不因此成为匹配对象。关注、收藏和创作记录也不自动转化为社交画像或邀请名单。若后续引入授权账号信息，应只使用用户明确同意的必要数据，并允许撤回。

刘看山形象为项目提供与知乎相关的视觉识别，用于标志和互助反馈；其使用仍需遵守相应素材授权范围。生态契合的主要依据是问题、知识贡献与自愿关系的设计。

平台接入状态

当前主项目尚未打通知乎内容检索、站内社区写入或认证账号闭环。开发工具具备调用条件不等于网页已集成相应能力，其他独立接入实验也不计入本产品完成度。

后续若开展内容接入，将通过官方开放能力少量获取允许使用的公开内容，经过缓存、来源标注与人工核验后呈现。AI 当前暂缓，不作为现有问答、整理或匹配能力进行展示。

六、整体技术实现方案

架构与分工

用户操作 → 网页视图与表单状态 → 同源 HTTP API → 房间及关系记录 → 服务端状态保存 → 页面读取与展示。

层次当前技术承担的职责
主界面HTML、CSS、JavaScript问题、交流、社区、卡片与好友视图；原生表单、对话框与响应式布局
卡片展示React、TypeScript、GSAP成果卡堆叠、切换与阅读交互；复用已挂载组件减少轮询重绘干扰
构建TypeScript 类型检查、esbuild将卡片组件编译为网页可加载的 JavaScript 与 CSS
业务服务Node.js HTTP 服务、REST 风格 API问题创建、房间匹配、消息、话题、卡片、成就及好友操作
数据保存浏览器存储与服务端 JSON 文件保存界面状态、交流记录和关系数据，支持原型恢复

采用这一结构，是为了用较少的运行依赖验证问题到成果的交互链路，并把展示组件与业务状态分开。文件存储适合单机原型，规模化服务需要进一步采用数据库、认证会话与权限模型。

核心数据关系

问题通过房间标识关联提问者、回应者、消息和社区话题；消息记录所属房间、发送者及文字内容。问题卡与完成记录关联房间，以房间识别重复保存和重复成就。好友申请关联共同房间及双方访客标识，通过后生成双向关系。

主项目尚未用服务端统一管理完整的总结与确认过程。下一步需为每个房间独立保存两方总结、关键句和确认状态，在服务端验证操作者、完成条件及成果唯一性。

同步与持久化

前端定时读取服务状态，同一浏览器来源的页面还通过 BroadcastChannel 和存储事件刷新显示。问题、消息、话题及卡片列表主要以服务端返回为准，并非具有冲突处理能力的离线合并。

localStorage 保存页面已写入的交流状态、访客档案标识、分类和成就；sessionStorage 保存当前标签页的角色、客户端标识及活动房间。问题、消息、话题、成果卡、成就和好友关系由服务端保存为 JSON，写入时使用临时文件替换。服务端状态位于网页发布目录之外。

同源标签页会共享访客档案，独立浏览器身份又不共享本地总结，因此双标签同步不能直接视为两个真实用户已完成全链路协作。完整的双人结束流程需要服务端确认记录支持。

运行与异常处理

完整交互依赖网页与业务服务一起运行。单独打开静态 HTML 可以查看页面，不能替代房间、发布和消息服务。

当前消息发送失败会保留输入框文字并提示重试，但尚无覆盖全部表单的离线草稿与重试队列。发布失败时的本地回退、状态覆盖和错误提示需要进一步修正，避免将未到达服务端的问题显示为发布成功。

访问与内容边界

页面采用文本转义和内容安全策略降低脚本注入风险，静态资源与会话数据分区保存。当前访客标识由客户端维护，部分接口有角色或成员检查，但尚不足以提供真实身份、私密房间或完整资源权限保障。

后续公开服务需要补齐认证、按房间与用户校验访问权限、输入限制、限流、备份恢复、举报与退出机制。浏览器存储和 JSON 文件不提供端到端加密或不可篡改保证。

八、优化与推进计划

先确保基础闭环可信

统一网页与业务服务的启动及状态检测，区分发布失败、已发布和进入房间失败。保留用户输入并允许明确重试。把总结与确认记录放到服务端按房间管理，使两个独立身份能够完成交流与成卡，避免依赖共享浏览器状态。

再完善双向交换

围绕一个小问题补齐情境、需求和贡献提示，验证表单是否真正帮助表达，而非增加填写负担。把复述与有效收获融入整理过程，保留可返回交流的路径。卡片应帮助用户回顾自己的理解，而不是仅拼接空白字段。

验证社区扩展和自愿关系

在核心流程稳定后，完善扩展内容预览、参与同意、离开房间和关系退出。邀请自愿参与者进行小范围试用，观察一对一交流在什么情况下需要更多人参与，再调整社区入口。

建立内容与公开服务条件

先完成少量公开来源的人工核验与引用设计，再评估正式内容接入。账号、数据库、权限、通知和治理能力按实际需求推进；取得用户同意并满足运行条件后再准备公开体验。AI 保持暂缓，不作为上述流程的启动条件。

九、初审展示与评价依据

计划书按照核心创作思路、整体技术实现、知乎生态契合度和场景价值展开，具体评价依靠可演示行为与可核验材料。

核心验收标准

  1. 新用户能独立发布或选择一个问题；提交失败时没有虚假的发布或入房成功提示。
  2. 两个独立身份可以进入同一房间、互发消息，并各自提交总结与确认。
  3. 只有两方确认后生成一张成果卡；重复提交不重复成卡，其他房间的状态不相互覆盖。
  4. 重新打开页面或恢复服务后，已保存的问题、消息、卡片与关系可恢复；未保存内容的处理清楚可见。
  5. 社区扩展与好友申请体现知情和自愿，成员操作遵守对应权限。
  6. 窄屏与键盘操作可完成主流程；动态效果不妨碍阅读与操作。

以上为验收目标，尚未形成真实用户效果结论。后续应记录首次完成率、等待回应情况、双方确认完成率、成果卡回看意愿及自愿继续交流情况，并结合失败原因调整产品。

本计划书说明项目内容、技术取舍和待完成范围，不替代可运行体验与实际验收材料。已有规则摘要将 AI 场景价值列为初审重点；当前暂缓 AI 会留下相应考核缺口。

十、内容与交付原则

网页只承载产品交互、原创示例和经过核验的必要公开内容。服务端会话、凭据、个人资料及原始研究材料与网页交付分离。涉及他人作品时保留来源并核对使用范围，不因公开可读就默认取得全文转载权。

用户对外分享共同成果前，应检查参与者意愿、个人信息和引用内容；产品后续应提供相应预览与控制。计划书、项目总结和网页本体分别维护，功能是否完成以实际产品和验收结果为准。
